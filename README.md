    ## 🛠️ 2. 내가 한 것 (What I Did): C++ 인벤토리 & 아이템 백엔드 설계

    UI를 담당하는 동료의 작업 속도에 맞추기 위해, UI가 아직 완성되지 않아도 독립적으로 동작할 수 있는 탄탄한 C++
  백엔드 구조가 필요했습니다.

    ### ① 데이터 에셋 기반 아이템 정의 (`URLItemDataAsset`)
    아이템 정보를 C++ 코드에 하드코딩하지 않고 기획자가 에디터에서 쉽게 만들 수 있도록 `UPrimaryDataAsset`을
  상속받았습니다.
    * 아이템 ID, 이름, 툴팁 설명, 아이콘 텍스처, 최대 중첩 수량, 아이템 유형(소모품/장비)을 정의했습니다.
    * 1차 테스트를 위해 체력을 회복시켜 주는 포션 에셋(`DA_Potion_Health`)을 생성해 두었습니다.

    ### ② 컴포넌트 분리 설계 (`URLInventoryComponent`)
    캐릭터 본체(`ARLCharacter`)에 아이템 배열을 직접 선언하면 클래스가 너무 무거워집니다. 유지보수를 위해
  `UActorComponent`를 상속받은 인벤토리 전용 컴포넌트를 분리했습니다.
    * 아이템 추가(`AddItem`), 사용(`UseItem`), 드롭(`DropItem`) 등의 핵심 API 제공
    * 추후 UI와 연동할 수 있도록 아이템 갱신 델리게이트 이벤트 선언

    ### ③ 협업을 위한 문서화 (`UI_INVENTORY_GUIDE.md`)
    UI 담당 팀원이 C++ 내부 코드를 일일이 분석하지 않아도 블루프린트에서 바로 호출할 수 있도록, **함수 시그니처와
  델리게이트 바인딩 방법**을 정리한 가이드 문서를 작성해 공유했습니다.

    ## 💥 3. 잘 안 된 것 (1): 한밤중의 Git C++ 충돌 (Merge Conflict)

    ### ⚠️ 문제 상황
    인벤토리 컴포넌트를 플레이어 캐릭터(`RLCharacter.h` / `RLCharacter.cpp`)에 등록하고 빌드하려던 순간, 보스 패턴을
  구현하던 동료가 '보스 공격 예고 데칼(Indicator)' 작업을 먼저 커밋/푸시했습니다.

    원격 변경 사항을 풀(Pull)해오자마자 캐릭터 헤더와 소스 파일 양쪽에서 **Merge Conflict**가 발생하며 프로젝트 빌드가
  멈췄습니다.

    ### 🛠️ 극복 및 해결 과정
    단순히 `Accept Theirs`나 `Accept Mine`으로 밀어버리면 상대방의 보스 공격 인디케이터나 내 인벤토리 컴포넌트 중
  하나가 통째로 유실되는 상황이었습니다.

    1. 충돌 마커(`<<<<<<< HEAD`, `=======`, `>>>>>>>`)를 직접 열어 양쪽의 수정 의도를 파악했습니다.
    2. 헤더 파일에서 공격 인디케이터 컴포넌트 선언과 인벤토리 컴포넌트 선언을 누락 없이 함께 병합했습니다.
    3. 소스 파일의 `BeginPlay()` 초기화 순서를 정리해 두 기능이 충돌 없이 실행되도록 재정렬했습니다.
    4. 로컬에서 언리얼 C++ 빌드와 에디터 구동 테스트를 거친 후 안전하게 머지 커밋을 완료했습니다.

    > **💡 배운 점 (Lesson Learned)**
    > 메인 캐릭터 클래스(`ARLCharacter`)는 모든 팀원의 작업이 교차하는 '위험 구역'이라는 점을 실감했습니다. 코어
  액터를 직접 수정하기보다는, 기능 단위로 **독립적인 `ActorComponent`**를 만들어 붙이는 구조가 협업 시 충돌을 방지하는
  최선의 방법임을 배웠습니다.

    ## 👻 4. 잘 안 된 것 (2): 잡몹이 보물상자를 뱉고, 보스는 아무것도 안 준다?

    ### ⚠️ 문제 상황
    인벤토리와 드롭 시스템을 붙이고 테스트 플레이를 해보는데 기괴한 현상이 발생했습니다.
    * 일반 잡몹을 잡았는데 최고급 보상 상자(`MyRLRewardChest`)가 100% 확률로 튀어나왔습니다.
    * 정작 보스(`BP_Boss`)를 처치했을 때는 상자가 나오지 않는 역전 현상이 일어났습니다.

    ### 🛠️ 원인 분석 및 해결 (`RLEnemyCharacter.cpp`)
    원인은 몬스터 사망 함수(`Die()`) 내부에서 일반 몬스터와 보스를 구분하는 분기 처리가 모호했고, 상자 스폰 로직이
  잘못 연결되어 있었기 때문이었습니다.

    ```cpp
    // 몬스터 사망 시 드롭 처리 수정
    void ARLEnemyCharacter::Die()
    {
        Super::Die();

        // 1. 보스 여부 자동 판정
        if (IsBoss())
        {
            // 보스 처치 시: 100% 확정보상 상자(MyRLRewardChest) 스폰
            SpawnBossRewardChest();
        }
        else
        {
            // 일반 몬스터: 필드 아이템 드롭(ARLItemDrop) 확률 계산
            TryDropFieldItem();
        }
    }

  • 일반 몬스터: 보상 상자 드롭 코드를 완전히 제거하고 필드 드롭 액터(ARLItemDrop)만 확률적으로 떨어지도록
  변경했습니다.
  • 보스 몬스터: 사망한 액터가 보스(BP_Boss)인지 클래스 및 태그로 자동 판정하도록 로직을 추가하고, 보스일 경우에만
  MyRLRewardChest 클래스를 비동기 로드하여 확정 스폰하도록 수정하여 버그를 완벽히 해결했습니다.

  ## 🚧 5. 협업 중 발생한 의존성 이슈와 방어 코드

  보상 상자를 열었을 때 뜨는 삼지선다 보상 선택창(WBP_RewardSelect) 에셋이 아직 UI 팀원의 작업 브랜치에 있어, 로컬에서
  에셋 누락 경고가 발생했습니다.

  • 작업물이 아직 합쳐지지 않은 상태에서도 게임이 튕기거나 크래시(Crash)가 나지 않도록 철저한 널 체크(Null-check) 방어
  코드를 작성했습니다.
  • 동료가 UI 작업을 마치고 푸시했을 때 코드 수정 없이 에셋만 꽂으면 바로 돌아가도록 환경을 격리해 두었습니다.
